# Markdown 标点边界加粗解析异常

## 验收结论

本问题已完成稳定复现、历史追溯、解析层修复和自动化验证，并于 2026-08-11 纳入已验收修复。修复后，AI 回答中的 `中文**“重点”**中文` 能按预期渲染加粗，不再显示原始 `**`，也不会因未识别的分隔符与后续加粗片段错误配对。代码区、未闭合标记、安全清洗和既有 Markdown 语法保持原有行为。

## 问题现象

当加粗内容以中文引号等标点开头或结尾，并且加粗标记直接嵌入中文正文时，页面可能显示原始星号，或者把后续原本独立的内容错误地连成一段加粗。例如：

```markdown
陶喆是华语乐坛的**“R&B教父”**，是一位音乐人。
这首歌是专辑中**“最诚实、最贴近陶喆内心”**的作品。
```

普通的 `中文**加粗**中文` 一直能够正常渲染，因此只检查不带边界标点的示例时很难发现该问题。

## 历史判断与根因

Git 历史表明，这不是后续功能迭代引入的回归：

1. [`markdown.ts`](../../apps/web/src/lib/markdown.ts) 在首个流式 Markdown 实现提交 `b7111db` 中创建；修复前该文件的全部代码仍归属于该提交。
2. 从初始提交到问题出现时，`markdown-it` 的锁定版本均为 14.3.0，解析器实现和配置没有发生版本漂移。
3. 后续加入的思考面板、流式自动滚动和长对话虚拟列表复用了同一渲染函数，只改变组件组合、更新时序或挂载范围，没有修改行内 Markdown 的分隔符判定。

根因是初始实现直接采用了 Markdown-it 的 CommonMark 强调规则，但没有为模型常见的中文标点输出补充兼容策略。CommonMark 使用左右侧邻接字符判断星号能否作为强调分隔符：

- 在 `正文**“重点` 中，`**` 前面是非空白正文，后面是标点，因此不能作为左侧开分隔符；
- 在 `重点”**正文` 中，`**` 前面是标点，后面是非空白正文，因此不能作为右侧闭分隔符。

Markdown-it 的行为符合规范，但不符合聊天产品需要接纳模型自然输出的场景。初始测试只覆盖了表格、任务列表、代码高亮、复制控件和安全清洗，没有覆盖加粗语法及中文标点边界，因而没有暴露这一兼容性缺口。

## 修复方案

在 Markdown-it 的行内状态层扩展 `scanDelims()`：

- 先完整执行 Markdown-it 原有的分隔符扫描；
- 仅处理长度至少为 2 的星号分隔符，不改变单星号斜体和下划线强调语义；
- 当默认规则拒绝开分隔符、且星号后是标点时，允许其打开加粗；
- 当默认规则拒绝闭分隔符、且星号前是标点时，允许其关闭加粗；
- 邻接字符按 Unicode 码点读取，并沿用 Markdown-it 自身的标点分类。

修复没有在渲染前对原始文本做全局正则替换。分隔符的分词、配对、嵌套、转义、代码区隔和未闭合处理仍由 Markdown-it 完成，因此不会把代码内容中的星号误改为标签，也不会隐藏不完整的流式输出。

## 回归测试

[`markdown.test.ts`](../../apps/web/src/lib/markdown.test.ts) 新增两组互补用例：

1. 使用与问题截图一致的中文正文、中文引号和 `R&B` 内容，验证标点包裹的短语与紧随其后的普通加粗片段分别生成正确的 `<strong>`，且输出不再包含原始 `**`。
2. 验证同类语法在代码跨度中保持原文，未闭合的星号仍作为普通文本显示，防止兼容规则越过 Markdown 的结构边界。

既有安全测试继续验证可执行 HTML 与 `javascript:` 链接不会进入最终输出。

## 最终效果

- 模型输出的中文标点包裹加粗内容能够稳定渲染。
- 一个无效分隔符不会再干扰后续独立的加粗片段。
- 标准加粗、单星号斜体、下划线强调和 Markdown 嵌套继续使用原生规则。
- 代码区和未闭合流式片段不会被预处理或错误改写。

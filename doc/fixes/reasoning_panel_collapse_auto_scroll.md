# 思考面板折叠后最终回答自动滚动中断

## 验收结论

本问题已完成稳定复现、修复、自动化验证和用户本地实测，并于 2026-08-08 验收。修复后，思考阶段结束并自动收起思考面板时，最终回答从首个片段开始持续自动向下滚动；用户主动上滚暂停跟随的既有行为保持不变。

## 问题现象

开启任一思考档位后，思考过程会在最终回答开始前自动折叠。部分视口中，最终回答只自动跟随一两行，随后视口停在旧位置；回答仍在后台继续接收和渲染，用户必须手动向下滚动才能看到后续内容。

问题集中发生在“展开的思考面板收起、最终回答开始增长”的阶段切换，而非普通非思考回答。使用 1404×451 视口、短思考内容和 80 行长回答的固定 E2E 场景可稳定复现：修复前重复 10 次全部失败，生成结束后视口距离底部约 1725–1726px。

## 根因

主对话区域原先只比较相邻两次 `scrollTop` 来判断用户是否主动上滚：

1. 思考阶段开始后，[`ReasoningPanel.vue`](../../apps/web/src/components/ReasoningPanel.vue) 自动展开，主对话内容和最大可滚动范围随之增高。
2. 收到 answer 阶段后，思考面板自动折叠，主对话内容高度和最大可滚动范围同时减小。
3. 浏览器为保证 `scrollTop` 不超过新的最大值，会自动把它向上钳制并触发 `scroll` 事件。
4. [`App.vue`](../../apps/web/src/App.vue) 只看到当前 `scrollTop` 小于上一次记录值，便把布局收缩误判为用户上滚，关闭 `followOutput`。
5. 后续消息更新和 `ResizeObserver` 发现跟随状态已关闭，因此不再把视口移到最新答案处。

布局调整与用户操作都可能表现为 `scrollTop` 减小，仅比较滚动方向不足以区分两者。

## 修复方案

主对话滚动状态现在同时记录：

- 当前 `scrollTop`；
- 最大滚动位置 `max(0, scrollHeight - clientHeight)`；
- 由两者计算出的底部距离。

当 `scrollTop` 向上移动时：

- 如果最大滚动位置同时减小，且视口到底部的距离没有增加，说明移动来自思考面板折叠或其他内容收缩，继续保持自动跟随；
- 如果底部距离实际增加，说明用户离开了底部，立即暂停自动跟随并显示“回到底部”；
- 重新进入距底部 96px 的范围后，仍按原规则恢复跟随。

`scrollToBottom()` 也同步刷新最大滚动位置，确保程序化贴底、内容尺寸观察和后续 `scroll` 事件使用同一份基线。计算保留 1px 容差，以兼容浏览器布局取整。

## 回归测试

[`chat.spec.ts`](../../e2e/chat.spec.ts) 新增“思考折叠后接长回答”用例：

1. 使用与问题截图一致的 1404×451 视口。
2. 选择高推理并发送固定测试消息。
3. 确认思考面板在 reasoning 阶段展开并显示完整测试思考。
4. 确认 answer 阶段面板自动折叠，随后生成包含 80 行代码的长回答。
5. 生成结束后检查：

   ```text
   scrollHeight - scrollTop - clientHeight <= 1px
   ```

修复前该用例重复 10 次全部失败，底部距离约 1725–1726px；修复后重复 10 次全部通过。完整 E2E 套件还保留“流式代码块持续跟随”和“用户主动上滚立即暂停”两条互补回归，防止修复通过强制贴底抢走用户阅读位置。

## 验证结果

- ESLint：通过，无错误或警告。
- TypeScript：shared、API、Web 和 E2E 类型检查全部通过。
- Vitest：shared 8 项、API 20 项、Web 18 项，共 46 项通过。
- Playwright：完整 10 项通过；新增用例另行重复 10 次，10 次全部通过。
- 生产构建：shared、Vue 前端和 Fastify API 全部通过。
- 用户本地实测：通过，确认最终回答在思考面板折叠后可持续自动向下滚动。

## 最终效果

- 思考面板自动折叠不会再关闭主对话的自动跟随。
- 最终回答从首个片段到生成结束持续贴近最新内容，包括长文本和代码块。
- 内容收缩造成的浏览器滚动位置钳制不会被误判为用户意图。
- 用户主动上滚仍会立即暂停跟随，流式请求与内容渲染不会被停止或截断。
- “回到底部”按钮和 96px 附近恢复规则保持不变。

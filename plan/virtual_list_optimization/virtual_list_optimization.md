# 长对话消息虚拟列表优化

## 目标

优化同一会话包含上百条消息时的前端渲染和滚动性能。消息总量增长后，页面只挂载当前视口及少量缓冲区内的消息，避免历史 Markdown、代码块和思考过程持续扩大 DOM、布局与绘制成本。

优化必须保持现有聊天体验：进入会话后定位到底部、流式输出时自动跟随、用户上滚后暂停跟随、回到底部后恢复跟随，以及思考过程展开、折叠和流式代码块增高时的滚动稳定性。

本计划先解决 Web 端渲染压力。首期继续一次性加载会话消息，不修改后端接口、数据库或模型上下文组装；是否增加历史消息分页由优化后的性能基线另行决定。

## 文档依据

方案以 2026-08-10 的 TanStack Virtual 官方文档为准：

- [Vue Virtual](https://tanstack.com/virtual/latest/docs/framework/vue/vue-virtual)：`@tanstack/vue-virtual` 提供 Vue 的 `useVirtualizer` 适配器。
- [Virtualizer API](https://tanstack.com/virtual/latest/docs/api/virtualizer)：提供动态元素测量、稳定 item key、overscan、总尺寸、索引滚动和尺寸变化后的滚动位置调整能力。
- [Vue Dynamic Example](https://tanstack.com/virtual/latest/docs/framework/vue/examples/dynamic)：展示未知高度列表项先估算、挂载后测量并修正布局的模式。

现有滚动行为以 [`plan/streaming_output/local_sse_chat_mvp.md`](../streaming_output/local_sse_chat_mvp.md) 和 [`plan/reasoning_chain_panel/deepseek_reasoning_chain_panel.md`](../reasoning_chain_panel/deepseek_reasoning_chain_panel.md) 中已经验收的约束为准，虚拟化不能改变这些语义。

## 当前基线

- `GET /api/conversations/:conversationId` 通过 Repository 查询并返回会话的全部消息；没有分页或数量上限。
- `useChat.loadChat()` 将完整消息数组一次性放入前端响应式状态。
- `App.vue` 使用普通 `v-for` 为每条消息创建 `ChatMessage`，没有虚拟列表或 `content-visibility` 隔离。
- 每条 assistant 消息可能同时包含答案 Markdown 和 `ReasoningPanel`。历史思考面板通过 `v-show` 折叠，折叠后内部 Markdown DOM 和组件实例仍然挂载。
- Markdown 渲染包含 `markdown-it`、代码高亮和 DOMPurify 清洗；历史消息在加载时需要全部解析并创建 DOM。
- `App.vue` 当前通过 `messages.map(...).join("|")` 监听全部消息的 ID、思考内容、正文和状态。流式消息每次增长时都会遍历并复制整段会话历史，工作量随历史文本总量增长。
- 主对话区域还使用内容级 `ResizeObserver`、`scrollHeight` 和 `scrollTop` 维护跟随状态；DOM 越大，相关布局读取和写入越昂贵。
- 当前 `apps/web/package.json` 没有虚拟列表依赖。

## 问题判断

静态代码审计已经确认存在长会话性能风险：

- 挂载的消息组件、Markdown 节点和历史思考内容数量随消息数线性增长。
- 初次打开长会话时，需要同步创建和测量全部消息 DOM。
- 用户滚动时，浏览器需要在更大的布局树上完成样式、布局、绘制和命中测试。
- 流式输出期间，全历史字符串监听会在高频更新路径上产生接近 `O(会话总文本长度)` 的额外工作。
- 每个已挂载思考面板的本地状态和观察器都会继续占用内存；虚拟化后这些成本应限制在可见范围内。

因此，仅替换消息列表渲染方式不足以完成优化；必须同时移除全历史拼接式监听，并重新建立适配动态高度虚拟列表的滚动跟随机制。

真实设备上的帧时间、长任务数量和内存基线尚未采集。实现开始前先建立可重复基准，作为参数调优和最终验收依据。

## 已确认范围

- 只虚拟化主对话区域的消息列表，不虚拟化左侧会话列表。
- 支持用户消息、答案 Markdown、代码块、思考面板和错误/停止状态等不同高度消息。
- 只挂载视口内消息和有限 overscan，消息总数不再直接决定 DOM 行数。
- 保持完整消息数组及现有共享 `ChatMessage` API 契约，不改变消息持久化和 SSE 协议。
- 保持现有单一生成任务和新消息追加到数组末尾的约束。
- 保持会话切换后默认定位到底部，不增加按会话恢复历史阅读位置。
- 同步优化流式更新监听、列表尺寸观察和重复布局读取。
- 增加 100、300、500 条消息的可重复性能夹具与回归测试。

## 技术方案

### 虚拟列表边界

新增 `VirtualMessageList.vue`，集中管理以下职责：

- `.conversation-scroll` 滚动容器及其稳定选择器。
- TanStack Virtual 实例、可见范围、总高度和动态测量。
- `followOutput`、底部距离、用户滚动方向和回到底部行为。
- 消息行挂载、稳定键、overscan 和尺寸变化后的滚动锚定。
- 对 `App.vue` 暴露回到底部能力，并通知是否需要显示“回到底部”按钮。

`App.vue` 继续负责会话、生成状态、输入区和错误提示，不再直接监听完整消息内容或维护第二套列表尺寸观察器，避免两个组件同时写入滚动位置。

### 动态高度布局

- 使用 `useVirtualizer`，`count` 始终与当前会话消息数一致。
- 通过总高度占位层保留完整滚动范围，只渲染 virtual items 对应的消息行。
- 每个挂载行携带虚拟索引并调用 `measureElement`，由实际 DOM 高度修正估算值。
- 初始估算按消息角色和内容类型给出保守值；最终参数以 100/300/500 条基准结果调优。
- 初始 overscan 以 6 条消息为候选值，最终值需要兼顾快速滚动空白和挂载 Markdown 的成本。
- 消息间距由虚拟器或统一行容器计算，不继续依赖无法计入测量缓存的外部 flex `gap`。
- 容器宽度变化、Markdown 异步尺寸变化、思考面板展开和折叠都必须触发对应行重新测量。
- 现有 `.message-row` 入场动画只用于真正新增的消息；历史行重新进入视口时不得重复播放动画。

### 稳定渲染键

当前乐观消息在收到 SSE `meta` 后会改写 `message.id` 和 `turnId`。虚拟器的尺寸缓存不能直接使用会变化的服务端 ID 作为唯一稳定键。

前端为每个消息对象分配仅用于当前页面生命周期的 `renderKey`：

- 历史消息加载和乐观消息创建时各分配一次。
- SSE 回填服务端 ID 时不修改 `renderKey`。
- `renderKey` 不加入共享 API、SQLite 或网络响应。
- 切换会话时清理旧会话的虚拟测量缓存和 UI 状态。

不得仅使用数组索引作为长期 key，以免删除未确认的乐观消息或替换会话数据后复用错误的高度缓存。

### 滚动跟随与锚定

虚拟化后的滚动状态遵守以下规则：

1. 初次加载会话、创建新 turn 或用户点击“回到底部”时，定位到最后一条消息的末端。
2. 用户处于底部跟随状态时，最后一条消息增长、代码块变高或思考面板收缩后继续贴底。
3. 用户主动向上滚动后立即关闭跟随；后续流式内容不得改变其阅读位置。
4. 用户重新滚入底部阈值内时恢复跟随。
5. 视口上方的消息从估算高度修正为实际高度时，调整滚动 offset 保持当前可见锚点不跳动。
6. 思考面板展开、折叠以及浏览器钳制最大滚动位置时，继续区分内容布局变化和用户主动上滚。
7. 程序化流式跟随使用即时滚动；用户点击“回到底部”可以保留平滑滚动，并在动态测量结束后进行一次精确校正。

底部距离使用虚拟列表总尺寸和当前 scroll offset 计算。现有 96px 恢复阈值继续保留，除非性能基线或回归测试证明需要调整。

### 响应式更新优化

移除 `messages.map(...).join("|")` 全历史监听，改为只观察会改变列表尾部和滚动状态的常量数量信号：

- 消息数组长度。
- 最后一条消息的稳定渲染键。
- 活跃 assistant 的 `content.length`、`reasoningContent.length` 和状态。
- 当前流式阶段和实际消息行高度变化。

由于当前应用只允许一个生成任务，活跃消息始终位于列表末尾；该约束使流式跟随无需扫描其他历史消息。实际尺寸变化以虚拟行测量结果为准，文本长度只作为调度信号。

移除主内容列的全量 `ResizeObserver`，由虚拟器只观察已挂载消息行。`ReasoningPanel` 自身用于内部滚动的观察逻辑继续保留，但实例数量会被虚拟范围限制。

### 思考面板状态

虚拟消息离开视口后会卸载，`ReasoningPanel` 当前组件内的 `open` 状态会丢失。展开状态需要提升到列表层，以 `renderKey` 保存：

- 活跃思考开始时自动展开，进入答案阶段自动折叠一次。
- 用户手动展开或折叠后，在该消息离开并重新进入视口时继续保持。
- 状态只在当前页面和当前会话内保存；刷新页面后历史思考仍按现有规则默认折叠。
- 会话切换时清理不再需要的状态，避免跨会话泄漏。

### 无障碍语义

- 虚拟容器继续提供列表语义，每个挂载消息提供 `role="listitem"`、`aria-posinset` 和 `aria-setsize`。
- 不再把整个会动态挂载和卸载的虚拟列表作为 `aria-live` 区域，避免用户滚动时重复播报历史消息。
- 新消息和生成状态使用独立、受控的 live region；不能在每个流式字符更新时重复播报完整回答。
- 消息角色、思考面板按钮、代码复制按钮和错误状态的现有可访问名称保持不变。

## 数据与 API 边界

首期不修改：

- `GET /api/conversations/:conversationId` 返回完整消息数组的契约。
- SQLite Schema 和消息顺序字段。
- `ChatMessage` 共享类型和 SSE 事件。
- 服务端 `getModelHistory()` 的完整模型上下文组装。

虚拟列表可以降低 DOM、布局和绘制成本，但不会降低完整响应载荷或前端消息对象的内存占用。如果 500 条以上会话的加载基线仍不可接受，再单独设计游标分页、向上加载和 prepend 锚点保持；该工作不能与首期虚拟化同时隐式引入。

- `apps/web/src/style.css`：总高度占位、虚拟行定位、间距和动画规则。
- Web Vitest、`e2e/chat.spec.ts` 及测试夹具：长会话与滚动回归。

## 性能基线

实现前构造固定随机种子的 100、300、500 条消息会话，内容至少覆盖：

- 短用户消息和多段长回答。
- 标题、列表、表格、引用和行内代码。
- 多语言代码块及语法高亮。
- 带思考过程和不带思考过程的 assistant 消息。
- 停止、错误和完成状态。
- 一条正在增长的流式回答。

在统一浏览器、视口和硬件环境记录：

- 会话加载到可交互的时间。
- `.message-row` 挂载数量和总 DOM 节点数量。
- 从底部滚到顶部再返回的 Performance Trace、长任务和帧时间。
- 流式输出期间脚本执行、样式计算和布局时间。
- JS heap 和 DOM node 内存占用。
- 自动跟随开启时的底部距离，以及暂停跟随后视口偏移是否稳定。

性能指标不在不稳定的共享 CI 环境设置绝对帧率门槛；CI 负责结构性约束和功能回归，固定本地环境的优化前后 Trace 负责性能验收。

## 实现顺序

1. 建立长会话测试数据生成器和 100/300/500 条基线，记录优化前结果。
2. 添加 `@tanstack/vue-virtual`，实现最小动态高度 `VirtualMessageList` 和稳定 `renderKey`。
3. 接入现有消息组件，完成总高度、行测量、overscan、间距和响应式宽度处理。
4. 将滚动跟随、用户上滚暂停、底部恢复和回到底部行为迁移到虚拟列表。
5. 移除全历史字符串监听和主内容列 `ResizeObserver`，只保留尾部消息与已挂载行的更新信号。
6. 提升思考面板展开状态，限制入场动画，并补齐虚拟列表无障碍语义。
7. 运行现有滚动、思考面板、代码块、会话切换和移动端回归，修复行为差异。
8. 采集优化后 Trace，与基线比较并调整估算高度和 overscan。
9. 完成全部验证后将状态更新为 `implemented_pending_acceptance`，等待用户验收；不在未验收时创建 `doc/` 最终文档。

## 测试计划

### 组件与状态

- 0 条、1 条和大量消息时正确计算虚拟范围。
- 相同视口下，消息总数从 100 增至 500 时挂载行数仍由可见范围和 overscan 决定。
- SSE 改写消息 ID 后 `renderKey` 和已测量高度缓存保持稳定。
- 删除未收到 `meta` 的乐观消息后，不复用错误行高或渲染错误消息。
- Markdown、代码块和思考面板改变高度后，总尺寸和后续行位置正确更新。
- 思考面板离开并重新进入虚拟范围后保留当前页面内的展开状态。
- 历史行重新挂载时不播放新消息入场动画。

### 滚动行为

- 初次进入长会话准确显示最后一条消息。
- 底部流式输出时持续跟随，底部距离保持在现有测试允许范围内。
- 用户向上滚动后立即暂停跟随，流式输出和行高变化不移动阅读位置。
- 用户滚回 96px 阈值或点击“回到底部”后恢复跟随。
- 视口上方消息重新测量时，当前可见消息及其屏幕位置保持稳定。
- 思考过程自动折叠、手动展开和长代码块增长不造成错误跳动。
- 快速拖动滚动条、连续滚轮和触摸滚动时不出现明显空白、重叠或顺序错乱。

### Playwright 与回归

- 通过测试环境直接写入或启动前 seed 生成 500 条消息，不通过生产 HTTP 调试接口造数。
- 从底部滚动到指定早期、中间和末尾消息，验证内容、顺序和定位。
- 断言 900×700 视口下 `.message-row` 数量保持在可见范围与 overscan 的设计上限内，而不是接近 500。
- 保留并通过现有“代码块增长时贴底”“用户上滚后暂停”“思考面板折叠后继续跟随”等测试。
- 验证会话切换、刷新恢复、停止生成、错误状态和 390px 移动视口无回归。
- 验证虚拟列表滚动时不会因行重新挂载而重复触发 live region 播报。

### 验证命令

- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`
- `pnpm test:e2e`
- `pnpm build`

## 验收标准

- 500 条混合消息时，只挂载视口及配置 overscan 内的消息行，DOM 行数不随总消息数线性增长。
- 长会话快速上下滚动时没有可见空白、消息重叠、顺序错误或持续跳动。
- 优化后固定环境 Performance Trace 的滚动长任务、布局成本和 DOM 内存相较基线有明确下降，并将结果记录到计划修订中。
- 流式更新不再扫描或拼接全部历史消息内容。
- 初次加载、持续跟随、用户上滚暂停、底部恢复和“回到底部”行为与现有版本一致。
- Markdown、代码高亮、思考过程自动折叠和手动展开在动态高度测量下正常工作。
- SSE 回填 ID、发送失败移除乐观消息和会话切换不会污染虚拟高度缓存或 UI 状态。
- 桌面端、移动端和键盘/辅助技术使用所需的现有语义不回归。
- lint、类型检查、全部 Vitest、Playwright 和生产构建通过。

## 已知限制与暂不包含

- 历史消息 API 分页、懒加载和向上加载更多。
- 模型上下文裁剪、摘要、归档或大规模上下文治理。
- 左侧会话列表虚拟化。
- 单条超长消息内部的 Markdown 分块虚拟化；单条消息在视口内时仍需完整渲染。
- 按会话恢复离开前的精确滚动位置；当前行为仍是切换后定位到底部。
- 原生浏览器“在页面中查找”无法匹配未挂载的离屏消息；如需要完整历史搜索，应另行提供基于消息数据的搜索能力。
- 服务端和前端完整消息数组的传输与对象内存优化。

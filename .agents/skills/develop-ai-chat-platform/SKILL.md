# AI Chat Platform 开发流程

把本文件作为该仓库的交付协议。优先服从用户当前指令；仅在用户未指定细节时使用以下默认流程。

## 先判定任务边界

1. 先读取 `git status --short`、当前分支、相关 `plan/`、`doc/`、代码与测试，保留已有未提交改动。
2. 严格解释用户动词：
   - “不动代码”“先分析”“先给方案”“先不实现”：只读诊断；除非用户明确要求写入 `plan/`，否则不改文件。
   - “按规范写入 plan”：只写计划及计划索引，不提前改业务代码。
   - “按照 plan 实现”：以对应计划为范围基线，开始实现和测试。
   - “检查/分析”：只报告证据；“修复/优化”才授权修改。
   - “提交”“推送”“合并”“创建 PR”：分别执行用户明确要求的 Git 动作，不自动扩展为下一步。
3. 对界面交互理解可能存在歧义时，先用具体场景复述状态变化、滚动方向和边界效果；用户要求先看方案时，得到一致结论后再实现。
4. 需要删除本地数据、会话或文件时，先只读定位精确目标、内容和级联范围；仅在用户明确授权后执行，并复核结果。

## 遵循分支约定

- 仅在用户要求创建或切换分支时操作分支。
- 先检查本地与远端既有命名，再使用小写 kebab-case：新功能通常为 `feat/<scope>`，修复或排版调整通常为 `fix/<scope>`。
- 不覆盖或清理用户已有改动，不主动删除功能分支。
- 需要合并时优先保持仓库的线性历史；不要为了“合并”制造空提交或不必要的 merge commit。

## 管理计划生命周期

先读取 `plan/README.md`，再按仓库规范维护计划：

- 路径使用 `plan/<snake_case>/<snake_case>.md`，并同步 `plan/README.md`。
- 使用现有 YAML 字段和日期格式；在文件末尾追加关键修订记录。
- 状态按真实阶段推进：
  - `draft`：仍在讨论或尚未确认。
  - `approved`：用户已确认范围，等待实现。
  - `implementing`：已经开始修改实现。
  - `implemented_pending_acceptance`：实现与内部验证完成，等待用户验收。
  - `accepted`：用户明确验收，或明确要求为已完成能力进行最终归档；此时必须存在对应 `doc/` 文档。
  - `superseded`：注明替代计划。
- 未经用户确认，不把 `draft` 或待验收计划提前标记为 `accepted`，也不提前创建最终功能文档。

计划至少写清：目标、当前基线与证据、范围与暂不包含、数据/API/UI 设计、兼容或迁移、异常与边界、实现顺序、测试计划和验收标准。涉及外部 API 或活跃依赖时，先核对官方一手文档；明确区分可验证事实、合理推断和待实测项。

## 按计划实现

1. 开始实现时把计划更新为 `implementing`，并将改动限制在已确认范围内。
2. 复用现有分层与契约；优先把复杂规则提取为纯函数或共享语义，而不是散落在组件中的条件分支。
3. 对异步流程显式处理乱序、取消、旧响应覆盖、状态切换和唯一标识；对数值显式区分有效的 `0` 与未知的 `null`。
4. 对 UI 同时考虑桌面端、移动端、浅色/深色、键盘、焦点、无障碍、溢出和虚拟列表动态高度。
5. 对 API、数据库和流式协议同时考虑旧数据、缺字段、异常终态、持久化恢复和失败降级；不得用估算值冒充上游实际值。
6. 对密钥只使用被 Git 忽略的 `.env`；不要输出密钥值，并在提交前确认敏感文件和临时脚本未被暂存。

## 做根因修复

对 Bug 或性能问题执行以下顺序：

1. 用用户给出的原始场景稳定复现，并建立会失败的回归测试。
2. 追踪完整数据流、事件时序或渲染链路；必要时使用 Git log/blame 判断是初始缺陷还是后续回归。
3. 在正确抽象层修复：例如共享语义 token、解析规则、状态机、请求序号或滚动意图，而不是只给当前按钮、组件或字符串打补丁。
4. 同时覆盖相邻边界，证明修复不会破坏标准行为、代码区、未闭合流、旧数据或其他主题/视口。
5. 不虚构性能结论。没有前后 Performance Trace 时，只陈述结构性风险和自动化证据，不声明具体耗时、帧率或内存降幅。

## 分层验证

先运行最接近改动的定向测试，修正后再从仓库根目录执行完整门禁：

```powershell
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
git diff --check
```

- UI 与滚动行为使用真实浏览器输入验证；Playwright 中优先使用真实鼠标、滚轮、触控或键盘动作，不用脚本改 `scrollTop` 冒充用户操作。
- 等待可观察的完成状态，不使用固定 sleep 作为通过条件。
- E2E 失败时先定向复现，再检查共享数据、遗留服务、端口和执行顺序；清理测试环境后重新跑完整套件。只有必要门禁最终通过，或已明确报告仍存在的失败，才结束任务。
- 测试数、构建提示和失败原因必须来自本轮实际输出，不沿用旧文档数字。
- 实现和完整验证结束后，将计划更新为 `implemented_pending_acceptance`，不要自行宣告用户验收。

## 按验收结果归档

用户确认验收或明确要求最终归档时：

1. 将计划改为 `accepted`，更新修订记录与 `plan/README.md`。
2. 已验收功能在 `doc/<feature>/` 新增最终文档，并更新 `doc/README.md`。
3. 根因不直观、容易复发、跨组件或包含取舍的重要修复归档到 `doc/fixes/`；简单低风险局部修复无需单独建档。
4. 最终文档至少包含源计划、验收结论、使用方式、最终实现/接口/配置、验证结果和已知限制。
5. 仅当用户可见能力、安装步骤或常用命令发生变化时更新根 `README.md`；不要为内部细节堆叠说明。
6. 保证 plan、doc、README 与真实代码一致，不写未运行的测试或未测量的收益。

## 安全提交与发布

1. 提交前检查 `git status`、完整 diff、范围、敏感信息和 `git diff --check`。
2. 显式暂存本次文件，复核 `git diff --cached` 后再提交；不要夹带测试产物或其他任务改动。
3. 参考 `git log` 选择 Conventional Commit，通常使用中文 `feat: ...` 或 `fix: ...`，类型必须反映实际变更。
4. “推送到 GitHub”默认用已配置的 `origin` 和 Git 凭据推送当前分支。`gh` 只在创建/管理 PR 等 GitHub 平台操作时需要；缺少 `gh` 不能阻塞普通 `git push`。
5. 未明确要求时不创建 PR。
6. 合并到主分支前先获取远端引用，确认工作区干净、提交范围和祖先关系；可快进时使用 `--ff-only`，再推送 `main`。发生分叉或冲突时先报告实际状态，不擅自改写历史。
7. 完成后确认本地与远端提交一致，并报告分支、commit、测试、文档状态和任何保留限制。

## 保持沟通可核验

- 使用中文，先给结论或当前结果，再给关键证据。
- 工作中简短报告已确认的基线、正在修改的层次、测试进度和真实阻塞。
- 最终交付链接到关键文件，并明确哪些测试已运行、是否提交/推送/合并、是否创建 PR。
- 术语要精确；当用户的表述与实现概念不同，先纠正术语再解释，不用模型生成的自述替代代码或协议证据。
